# Hunter v1.7 자동화 설계 근거와 적용 범위

조사일: 2026-09-12. 공식 프로젝트·공급자 문서를 확인하고 Hunter의 현재 Go·React·PostgreSQL 구현과 대조했습니다. 아래 열 가지는 제품 기능의 복제가 아니라 운영 문제를 참고해 작성한 Hunter 자체 코드입니다. 고정된 PentAGI 원본 312파일과 라이선스 경계는 변경하지 않습니다.

## 구현한 열 가지 운영 기능

| 기능 | 관리자가 설정하는 것 | 실행과 한계 |
| --- | --- | --- |
| 1. 동적 수신자·당직 | 활성 사용자 연락처, 관리자 확인 여부, 조직·당직 기간, 규칙의 수신자 소스 | 담당자·서비스 소유자·조직·당직을 현재 권한으로 다시 계산. 개인 연락처 자가 인증이나 자동 OTP 검증 아님 |
| 2. 알림 묶음·발송 한도 | 5~1440분 창, 수신자별 시간당 한도, 긴급 심각도 | 현재 이벤트를 묶어 알림 수를 줄임. 긴급 예외는 묶음·한도를 건너뜀 |
| 3. 영업일 기한 예고 | IANA 시간대·업무 요일·휴일·예고 영업일 | 수동 기한 또는 활성 SLA의 유효 기한을 사용. 공휴일 인터넷 자동 다운로드 없음 |
| 4. 업무 확인·미확인 대응 | 업무 확인 한도와 `finding.unacknowledged` 규칙 | 지정된 현재 수신자가 확인. 승인·취약점 해결과 별도이며 계층형 자동 전화 호출은 없음 |
| 5. 조직 주간 요약 | 요일·시각과 `team.weekly` 규칙 | 동적 사용자는 현재 접근 가능한 서비스, 관리자 지정 고정 주소는 해당 조직 전체 합계를 전달. 해결 수는 현재 해결 상태와 기간 내 변경 시각 기준이며 실제 해결 전환 횟수·MTTR 아님 |
| 6. 전달 결과·대체 채널·채널 보호 | 결과 조회·Hunter 서명 콜백·동일 수신자 계열 대체 채널·실패 임계치 | 명시적 실패에만 한 단계 대체. 불명·미조회·충돌은 자동 재발송 금지. 새 메시지로 임의 시험하지 않고 기존 허용 대기 건으로 보호 해제 후 처리 |
| 7. 변경 영향별 검사 선택 | 서비스·연동·이벤트와 경로/API/구성요소/권한 패턴 → 프로파일·범위·시나리오 | 서명된 실제 변경 목록과 매칭된 검사만 현재 정책으로 요청. SAST·컨테이너 엔진의 자동 설치·실행은 아님 |
| 8. ITSM 양방향 동기화 | 기존 외부 티켓의 GET 주소·필드 매핑·주기·배포 확인 재검증 | 기존 명시적 POST 발송 뒤 GET/서명 콜백으로 담당자·기한·외부 상태를 동기화. 완료만으로 해결하지 않고 충돌 시 유지 |
| 9. 발송 없는 모의 검사 | 저장된 규칙·기간·검사 상한 | 보관된 이벤트를 현재 설정·자료·수신자로 추정. 과거 시점의 정확한 재연이나 실제 전달 보장 아님 |
| 10. 알림 본문 보존·파기 | 보존 일수, 건별 보존 고정과 사유 | 적격 종결 건의 본문·수신 정보·시도 상세만 파기하고 중복 식별 기록 유지. 백업·외부 공급자의 사본을 소급 삭제하지 않음 |

## 폐쇄망 적용

관리 설정·연락처·비밀값·대기 본문·동기화 이력은 같은 PostgreSQL을 사용합니다. 서비스 환경변수 네 개와 단일 서비스 이미지를 유지하며 시간대 데이터도 이미지에 포함합니다. 알림·결과 조회·ITSM 폴링은 제어 서버에서만 실행하고 진단 전용 워커는 발송하지 않습니다.

외부망 연결이 없는 조직은 허용된 사내 SMTP·메시지·ITSM 게이트웨이를 준비합니다. Hunter 콜백은 `X-Hunter-Timestamp`와 `X-Hunter-Signature`, 정규화한 본문을 사용하는 **별도 계약**입니다. GitHub의 `X-Hub-Signature-256`이나 공급자 고유 콜백을 그대로 받는 호환 엔드포인트가 아닙니다. 타임스탬프와 원문 바이트가 달라지면 서명도 다시 생성해야 합니다.

## 상태 해석과 검증 범위

SMTP/API 접수, 공급자 전달 결과, 사용자의 업무 확인, 팀장 승인, 발견 건 해결은 별도로 저장합니다. 결과 조회가 실패하거나 상충하면 전달 실패로 추정해 자동으로 다시 보내지 않습니다. 설정·채널 버전이 달라진 과거 receipt를 새 규칙으로 다시 해석하지 않으며 같은 전달 ID에 receipt가 있으면 수동 재전송도 차단합니다.

검증에는 격리된 PostgreSQL과 로컬 모의 SMTP·HTTP·티켓 서버를 사용합니다. 실제 공급 계정, 유료 발송, 단말 수신, 카카오 템플릿 승인·읽음은 별도 운영 확인 대상입니다. 현재 수행 결과와 공개 아티팩트 검증은 [검증 기록](validation.md), 사용 순서는 [관리자 가이드](guides/admin-guide.html#13-10-자동화-관리-시작하기)를 기준으로 합니다.
