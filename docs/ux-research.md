# Hunter 목록 사용성 조사

조사일: 2026-09-12 · 기준: Hunter v1.2.0 (`670500c`)

서비스 자산과 발견 건 목록을 반복해서 사용하는 업무를 기준으로 개선 우선순위를 정리했다. 공식 자료의 지침, 현재 화면에서 관찰한 사실, Hunter에 적용할 제안을 구분한다. 앞부분은 v1.2.0 관찰과 개선 제안이며, 이후 구현·검증 결과는 마지막 절에서 별도로 기록한다.

## 조사 범위와 방법

- NN/g, IBM Carbon, 미국 USWDS, 영국 DWP의 원문을 검색하고 읽었다. DWP 자료는 정식 공통 컴포넌트 규격이 아닌 `Contribute → Open questions → Filters`의 설계 논의다.
- 로컬 서비스의 v1.2.0 웹 번들을 Chromium에서 실행했다. 서비스·발견 건 API 응답만 브라우저 안에서 37건의 합성 자료로 대체했다. DB에 자료를 추가하거나 진단을 실행하지 않았다.
- 1512×1050 및 390×844 화면에서 기본 목록, 50개 표시, 심각도 필터, 세로·가로 스크롤을 관찰했다. 표시 개수 50은 실제 37개 행을 한 화면 목록에 담는 조건이다.
- 코드에서는 `web/src/resources.tsx`, `use-list-view.tsx`, `list-view.ts`, `list-view.css`, `navigation.ts`의 현재 동작을 확인했다.
- 한국어 검색, 정렬, 페이지 이동, URL 상태, 상세 새로고침, 빠른 이동은 v1.2.0에서 이미 제공하므로 신규 제안에서 제외했다.

실제 사용자 인터뷰나 업무 수행 시간 비교 실험은 수행하지 않았다. 아래 수치는 재현 가능한 화면 관찰이며, 생산성 향상률·사용자 만족도·WCAG 인증 또는 전체 접근성 적합성을 뜻하지 않는다.

## 현재 화면에서 확인한 문제

### 1. 필터 결과와 상단 건수가 서로 다르게 읽힌다

발견 건 37개에서 `심각도: 심각`을 선택하면 결과는 8개다. 상단의 `발견 건 목록` 옆 배지는 계속 `37`이며, `8건 / 조회 37건`은 표 하단에 표시된다. 하단 결과 수의 시작 위치는 데스크톱에서 화면 위로부터 약 1,153px, 모바일에서 약 1,360px였다. 두 화면 모두 첫 화면에서는 결과 수를 볼 수 없었다.

각 Select에는 이미 선택값과 해제 버튼이 있다. 불편은 개별 해제 기능의 부재가 아니라, 검색어와 여러 조건을 모아 확인하는 요약 및 결과 수가 결과 시작 부분에 없다는 점이다. 이 차이는 업무자가 결과 8개를 전체 37개의 일부 페이지로 오해할 가능성을 만든다. 이 가능성은 화면 구조에 근거한 해석이며 실제 사용자 오해 발생률을 측정한 것은 아니다.

### 2. 긴 표를 읽을 때 열 제목과 항목 이름을 놓친다

50개 표시를 선택해 37행을 펼치면 서비스·발견 건 표 높이는 약 3,135px, 첫 행 높이는 약 83px였다. 헤더의 계산된 CSS 위치는 `static`이다. 데스크톱에서 문서를 850px 내린 뒤 발견 건 헤더는 화면의 -438~-372px 위치로 사라졌다.

390px 화면에서 발견 건 표를 가로로 끝까지 이동하면 제목 셀은 -395~-156px로 화면 밖에 놓였다. 오른쪽의 담당자나 작업 메뉴를 보면서 어떤 발견 건인지 확인하려면 가로로 되돌아가야 한다. 이는 문서 전체의 가로 넘침 오류와는 다른, 표 안의 탐색 비용이다.

### 3. 반복 조건에 이름을 붙여 다시 열 수 없다

현재 URL에는 검색·필터·정렬·페이지가 남고 새로고침도 보존된다. 하지만 `운영 결제 서비스`, `심각한 확인 건`처럼 조건 묶음에 이름을 붙여 목록 안에서 다시 선택하는 동작은 없다. 빠른 이동의 즐겨찾기는 메뉴 경로를 저장하므로 특정 조회 조건의 저장과 구분된다.

같은 조건을 자주 쓰는 업무에서 저장 보기가 유용하리라는 판단은 Hunter에 대한 설계 가설이다. 위 원문들이 Hunter 사용자에게 저장 보기를 요구한다고 결론 내린 것은 아니다.

## 권장 개선 세 가지

| 우선순위 | 개선 | 적용 대상과 구체적인 동작 | 완료 확인 |
| --- | --- | --- | --- |
| P1 | 적용 조건 요약과 상단 결과 수 | 공용 목록의 검색·필터 아래에 `결과 8건 / 조회 37건`을 표시한다. `심각도: 심각`, `검색: 결제`처럼 이름과 값을 갖는 해제 버튼을 제공한다. 한 조건의 해제는 다른 조건·정렬·표시 개수를 보존하고 페이지는 유효한 첫 페이지로 맞춘다. 전체 초기화는 기존 동작과 구분한다. | 0건·1건·여러 조건·긴 한글 조건을 확인한다. 개별 해제 후 URL·입력값·결과 수가 일치하고, 키보드 초점과 뒤로 가기가 예측 가능해야 한다. |
| P1 | 표의 읽기 문맥과 여백 선택 | 긴 표에 최대 높이를 둔 스크롤 영역과 헤더 고정을 적용하고, 넓은 화면의 가로 스크롤에서는 이름·제목 열을 고정한다. `기본 / 촘촘하게` 같은 행 여백 선택은 글자 크기를 줄이지 않고 수행한다. 표 아래 페이지 이동은 계속 접근 가능하게 둔다. | 25·50·100개 표시, 짧은 목록, 긴 제목, 200% 확대, 키보드 가로·세로 이동을 확인한다. 고정 헤더·식별열이 셀이나 작업 메뉴를 가리지 않고, 문서와 표 사이에 스크롤 갇힘이 없어야 한다. |
| P2 | 사용자별 저장 보기 | 서비스·발견 건의 검색·필터·정렬·표시 개수에 짧은 이름을 붙여 저장·적용·삭제한다. 다른 사용자와 목록 종류를 분리한다. 페이지 번호와 특정 상세 항목 ID는 저장에서 제외해 오래된 위치로 열리는 일을 피한다. | 동일 사용자 재방문, 계정 전환, 잘못된 저장값, 사라진 서비스 필터, 삭제, 저장 실패를 확인한다. 선택한 보기의 조건을 다시 바꾸면 현재 상태가 저장본과 다름을 표시한다. |

표 헤더와 왼쪽 식별열을 고정하는 방식은 Hunter의 화면 관찰에 따른 제안이다. 특히 USWDS의 구성 제한 때문에 이 조합이 자동으로 안전하거나 접근 가능하다고 전제하지 않는다.

저장 보기를 브라우저에 저장한다면 사용 범위를 `이 브라우저의 내 보기`로 알린다. 저장 자료에는 조회 조건과 이름만 넣고 API 응답, 결과 행, 비밀값을 복제하지 않는다. 보기의 복원은 현재 API 권한을 그대로 적용해야 하며, 과거에 접근했던 서비스의 데이터를 다시 허용해서는 안 된다.

## 적용 범위와 보류

이 조사에서 제안하는 범위는 목록을 읽고 다시 찾는 흐름이다. 실제 적용 여부와 최종 동작은 구현·검증 후 사용자 가이드에 반영한다.

| 우선 적용 제안 | 공용 목록의 조건 요약·상단 결과 수, 서비스·발견 건의 표 읽기 개선, 사용자별 저장 보기 | 실제 v1.2.0 화면에서 확인한 반복 탐색 비용을 줄인다. |
| 함께 검증 | 320·390px에서 고정 열 비활성화 또는 폭 제한, 표 여백 선택, 긴 조건 이름, 키보드 초점 | 모바일 첫 열이 화면 대부분을 가리거나 작은 버튼·글씨를 만드는 부작용을 피한다. |
| 유지 | 기존 한국어 검색·의미 기반 정렬·페이지·URL 상태·상세 이동·빠른 이동 | 이미 제공하는 기능을 다시 만들지 않는다. |

| 보류 | 무한 스크롤·셀 직접 편집·대량 상태 변경 | 기존 페이지 위치·업무 권한·승인 절차까지 바꾸는 별도 작업이다. |
| 보류 | 모든 모바일 표의 카드 전환, 모든 필터의 일괄 적용 전환 | 비교·정렬 가능한 표 구조와 현재 빠른 필터의 장점을 잃을 수 있다. 실제 업무 실험 뒤 판단한다. |

조회 한도는 별개다. 자산·발견 건 등의 리소스 목록은 서버가 반환한 종류별 최근 최대 5,000건, 에이전트·감사 목록은 최근 최대 1,000건 안에서 동작한다. 저장 보기·표 밀도·브라우저 페이지 수를 늘려도 서버의 전체 이력 검색 기능이 생기는 것은 아니다.

## 구현 후 검증 기록 원칙

검증에서는 기능 완료와 접근성 평가를 구분한다. 조건 해제·보기 저장·스크롤·키보드·초점·확대·모바일 검사를 실제로 수행한 범위만 기록한다. 디자인 시스템이 자체 접근성 검사를 통과했다는 사실을 Hunter의 WCAG 인증이나 전체 적합성으로 옮겨 쓰지 않는다.

조사 당시 관찰 원자료는 개발 환경의 `.tmp/ux-checks/v120-observation.json`에 남겼다. 공개 가이드의 실제 서비스 캡처와 달리 이 조사용 화면은 API 응답을 대체한 합성 자료이므로 제품 성능이나 실제 보안 진단 결과의 근거로 사용하지 않는다.

## v1.3.0 구현과 브라우저 검증

2026-09-12 최종 Go 실행 파일이 제공하는 v1.3.0 화면에서 위 세 제안을 구현한 공용 목록 도구를 검증했다. 61개 합성 항목을 제공하고 50개 표시를 선택한 뒤 1512·700·390·320px에서 32개 기능 검사를 수행했다. GET 응답만 브라우저에서 대체했으며 서버 자료를 변경하지 않았다.

| 제안 | 구현한 동작 | 확인한 결과 |
| --- | --- | --- |
| 결과와 조건 표시 | 표 위의 결과·조회 수, 검색어·필터별 해제 버튼 | 여러 조건·0건·긴 한글 조건, 개별 해제 시 다른 조건 보존을 확인했다. |
| 표 문맥과 간격 | 높이 제한 스크롤·헤더 고정, 640px 초과 첫 열 고정, 기본/촘촘하게, 전체 펼치기 | 700px 화면에서 가로 103px 이동 후 첫 열 위치가 유지됐다. 모바일에서는 첫 열이 함께 이동했다. 측정 행 높이는 약 83→69px로 줄었고 해당 행의 모든 검사 대상 글자 크기는 동일했다. |
| 저장 보기 | 사용자·메뉴별 이름 있는 조건, 브라우저 저장, 적용 시 첫 페이지 | 저장·적용·삭제·새로고침·같은 브라우저의 사용자 전환·메뉴 분리를 확인했다. |

각 화면에서 JavaScript 오류·예상치 않은 HTTP 오류·문서 가로 넘침은 관찰되지 않았다. 키보드로 스크롤 영역에 접근해 방향키로 이동했고, 초점 표시를 확인했다. 표를 펼치면 세로 스크롤 주체가 문서가 되므로 헤더가 화면 위에 고정되지 않는 예외를 사용자 가이드에 설명한다.

키보드로 조건 칩을 해제할 때 초점이 문서 본문으로 돌아가는 문제를 발견해 수정했다. 남은 조건이나 검색 입력으로 초점을 복구하는 동작을 최종 실행 파일에서 네 화면 너비 모두 다시 확인했다. 최종 내장 빌드에서는 검색 지우기·전체 초기화·중간 및 마지막 조건 해제·저장 보기 적용·표 설정 닫기의 여섯 초점 복귀 경로도 확인했다. 상세 결과는 [검증 기록](validation.md)에 함께 남긴다. 32개 검사의 원자료는 `.tmp/ux-checks/v130-list-regression.json`에 보관한다. 이 결과는 사용자 연구·업무 효율 향상률 측정·전체 접근성 적합성 평가를 대신하지 않는다.

### 폼 오류와 키보드 탐색에 함께 적용한 근거

목록 외에도 입력 복구와 반복 메뉴 건너뛰기를 개선했다. 다음은 원문에서 선택해 적용한 내용이며 해당 문서의 모든 패턴이나 WCAG 성공 기준을 구현했다고 주장하지 않는다.

| 원문 | 채택한 내용 | Hunter 적용과 검증 범위 |
| --- | --- | --- |
| [GOV.UK — Error summary](https://design-system.service.gov.uk/components/error-summary/) | 오류 요약으로 초점을 옮기고 오류가 있는 입력으로 링크한다. | 관리자 설정·개인 프로필·비밀번호의 요약·항목 오류를 연결했다. 필수값 오류에서 Tab·Enter로 입력에 도달하는 동작을 확인했다. |
| [GOV.UK — Recover from validation errors](https://design-system.service.gov.uk/patterns/validation/) | 실패한 입력을 유지하고 제출 시 수정할 내용을 알린다. 입력 검사는 서버의 권한·유효성 검사를 대신하지 않는다. | 모의 서버 실패에서 설정·프로필·비밀번호 입력을 유지했다. 설정 그룹별 저장, 미저장 이동 안내, 저장 성공·실패와 초안 보존을 여섯 시나리오로 확인했다. 비밀값 초안은 메모리에만 두며 성공 후 지웠다. |
| [W3C — G1 본문 바로가기](https://www.w3.org/WAI/WCAG22/Techniques/general/G1) | 첫 탐색 링크로 반복 영역을 건너뛰고 본문에 초점을 둔다. | 첫 Tab의 본문 바로가기와 페이지 이동 후 제목 초점을 확인했다. 검색어 변경 같은 같은 페이지 작업에서는 입력 초점을 유지했다. |
| [W3C — Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html) | 키보드 초점의 현재 위치를 시각적으로 알 수 있어야 한다. | 공용 초점 테두리, 모바일 메뉴의 닫힌 영역 탐색 제외, 열린 메뉴의 초점 유지·Esc 복귀를 적용했다. 320·390·1512px에서 키보드 흐름과 대화상자 복귀를 확인했다. |

키보드와 폼 검증은 로컬 Chromium, 합성 API 및 모의 실패 응답으로 수행했다. 스크린 리더 전체 조합, 실제 사용자 숙련도·장애 특성, 모든 확대·고대비 환경을 평가한 것은 아니다. 브라우저 새로고침·닫기의 미저장 경고와 설정 그룹 간 이동 안내를 제공하지만, 다른 업무 메뉴로 이동하는 모든 SPA 탐색을 차단하지는 않는다. 이 범위는 관리자 가이드에 명시했다.
