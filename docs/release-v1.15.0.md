# Hunter v1.15.0

**방문 추적**의 허용 원점 판정을 관리자 화면에서도 서버 계약과 같게 맞춘 릴리즈입니다. **보안 정책에서 차단된 출처** 패널이 제안한 원점이나 설정 화면이 통과시킨 초안이 저장 시 거절되던 차이를 없앴습니다. 서버 파서·저장된 설정·권한은 달라지지 않으며 일반 PostgreSQL·네 환경변수·서비스 Docker 이미지 하나의 기본 배포를 유지합니다.

## 사용자가 달라지는 점

- **화면이 제안한 원점이 저장에서 거절되지 않습니다.** 차단된 출처 패널의 "허용 목록에 추가" 와 설정 화면의 사전 검사는 지금까지 브라우저 URL 파서로 원점을 읽었습니다. 파서는 `http://0177.0.0.1`·`http://0x7f.1`·`http://2130706433` 같은 옛 IPv4 별칭을 정식 주소로 접어 버리는데, 서버의 `trackingOrigin`(`internal/app/tracking.go`)은 별칭이 앱 원점 거부를 우회하지 못하도록 이를 거절합니다. 숫자 최상위 라벨, 퍼센트 인코딩된 호스트, 라벨 63바이트·호스트 253바이트 길이, 포트 1~65535 범위도 파서는 검사하지 않았습니다. 이제 화면이 같은 규칙을 원문 텍스트에 직접 적용하므로 버튼이 제안하는 원점은 `PUT` 이 받는 원점과 같습니다.
- **`xn--` 라벨을 화면에서 직접 해독합니다.** 이미 ASCII 인 ACE 라벨을 URL 파서마다 다르게 처리해(런타임에 따라 `xn--a.internal` 을 그대로 돌려주거나 거절) 화면과 서버의 판정이 갈렸습니다. 이제 서버가 `idna.Lookup.ToASCII` 로 하는 것과 같게 RFC 3492 해독을 화면에서 수행하고 그 결과만 파서로 다시 인코딩합니다. 해독할 수 없거나 평범한 ASCII 로 풀리는 라벨은 런타임과 무관하게 거절합니다.
- **전체 길이를 서버와 같은 방식으로 셉니다.** 허용 주소의 1,536바이트 합계는 원문을 이어 붙인 길이가 아니라 서버처럼 **중복을 제거한 원점마다 `len+1`** 로 계산합니다. 원점 최대 10개, 각 300바이트, Hunter 자신의 원점 거부는 기존과 같습니다.
- **저장된 설정은 그대로입니다.** 이번 변경은 관리자 화면(`web/src/tracking-state.ts`)의 제안과 사전 검사에만 적용됩니다. 서버 파서, 이미 저장된 허용 목록, 추적 revision, 미리보기 5분 1회, 격리 iframe 과 고정 path·title 수집 범위, 로그인·관리자·개인화 화면 제외는 달라지지 않습니다.

## 운영 조건과 한계

방문 추적은 여전히 **기본 꺼짐**이며 관리자 세션 전용입니다. 이 변경은 화면의 사전 검사를 서버 판정에 맞춘 것이고 서버 검사를 대체하지 않습니다. 저장 여부는 언제나 `PUT` 의 `trackingOrigin` 결과로 결정됩니다. IPv4 사상(mapped) IPv6 리터럴은 화면에서 압축 형식으로, 서버에서 점 표기로 정규화되며 서버는 두 형식을 모두 받습니다. 앱 전체 CSP 를 완화하지 않았고 관리자 설정 항목·API 계약·권한은 추가하거나 바꾸지 않았습니다.

## 검증과 배포

`internal/app/testdata/tracking-origins.json` 의 공유 벡터(원점 78개, 차단 출처 22개, 초안 5개 — 합계 105개)를 Go 의 `TestTrackingOriginVectors` 와 프런트엔드의 `tracking-state.test.mjs` 가 같은 파일에서 읽어 한 파일로 두 구현을 고정합니다. 릴리즈 커밋에서 실행한 검사와 건너뛴 검사는 [검증 기록](validation.md)에 적었습니다.
