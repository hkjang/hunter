# Hunter v1.23.0

**진단 허용 범위**와 **실행 정책**의 숫자 칸 일곱 개가 서버가 실제로 받는 범위를 선언하도록 고친 릴리즈입니다. 범위 안의 값이 만드는 요청은 한 글자도 달라지지 않으며 서버 API·권한·감사 기록, 일반 PostgreSQL·네 환경변수·서비스 Docker 이미지 하나의 기본 배포를 유지합니다.

## 사용자가 달라지는 점

- **폼이 조작자를 서버가 거절하는 값으로 데려갔습니다.** `web/src/resources.tsx` 의 숫자 칸은 Mantine `NumberInput` 이고 이 컨트롤의 `clampBehavior` 기본값은 `"blur"` 입니다. 즉 선언한 `min`·`max` 는 참고 문구가 아니라 **칸을 떠날 때 타이핑한 값을 그 경계로 옮기는 동작**입니다. 그런데 선언한 상한은 `internal/app/policy.go` 의 `validateScope`·`validatePolicy` 가 판정하는 표와 달랐습니다. 실행 정책의 **동시 실행 상한**은 서버가 `1` 만 받는데 폼은 `20` 까지, 두 자원의 **최대 요청 수**는 서버가 `100` 까지인데 폼은 `1000` 까지, **실행 제한 시간 (초)** 는 서버가 `300` 까지인데 폼은 `600` 까지 올려 줬습니다. **초당 최대 요청 수**도 서버 상한이 `5` 인데 폼은 `100` 이었습니다. 조작자는 폼이 허용한 값을 저장한 뒤에야 `400` 을 보았습니다.
- **1 미만의 초당 요청 수는 0 으로 잘려 거절됐습니다.** 자원 저장 처리기는 `internal/app/server.go:129` 에서 `json.NewDecoder` 로 본문을 읽고 `UseNumber` 를 쓰지 않으므로 JSON 숫자는 `float64` 로 도착하고, `number()`(`internal/app/domain.go:115`)가 `int(n)` 으로 돌려줍니다. 두 검증의 검사는 `n < 1 || n > b.max` 이므로 **초당 최대 요청 수**의 옛 `min` 이던 `0.1` 부터 `0.9` 까지 모든 값은 `0` 으로 잘려, 타이핑한 값이 넘은 것처럼 보이지 않는 하한을 넘었다는 이유로 `400` 이 됐습니다.
- **소수점은 말없이 버려졌습니다.** 같은 경로에서 두 검증은 잘린 정수를 `m[b.k] = n` 으로 되써 저장합니다. 그래서 제출한 `2.7` 은 `400` 이 아니라 **아무 안내 없이 `2` 로 저장**됐습니다. 이제 선언에 `integer` 가 붙은 칸은 입력에서 `allowDecimal={false}` 로 소수점을 막습니다. 이 잠금은 선언에서 읽으므로 공유 렌더러를 쓰는 다른 숫자 칸, 즉 발견 건의 기여 점수(`contribution_points`)와 예약의 반복 간격(`interval_minutes`)은 그대로입니다.
- **상한은 공유 표 하나에서 옵니다.** 일곱 칸의 `min`·`max`·정수 잠금은 이제 `web/src/resource-form-state.ts` 의 `resourceNumberBounds` 한 곳에 있고 각 선언이 그것을 펼쳐 씁니다. 선언이 흩어져 다시 어긋나는 일을 막고, 시험이 표 한 곳만 보면 되도록 하기 위해서입니다.
- **하한은 올리지 않고 1 로 둡니다.** 서버 표의 둘째 칸(`max_requests` 의 `10`, `timeout_seconds` 의 `30`)은 하한이 아니라 값이 없거나 숫자가 아닐 때 `number()` 가 쓰는 **대체값**입니다. 검사는 `n < 1 || n > b.max` 이므로 일곱 칸 모두 `1` 부터 받습니다. 하한을 `10` 이나 `30` 으로 선언하면 서버가 받는 더 안전한 쪽 값을 폼이 거절하고, 이미 그보다 작은 값으로 저장된 행은 조작자가 그 칸을 한 번 지나가는 것만으로 값이 위로 올라갑니다. 그래서 공유 하한은 서버의 실제 하한인 `1` 이며, 이 값이 올라가면 Go 시험이 실패합니다.

## 운영 조건과 한계

서버 계약은 바꾸지 않았습니다. 일곱 필드의 API 형식·권한 검사·감사 기록과 `validateScope`·`validatePolicy` 의 표, 일반 자원 수정의 `expected_updated_at` 비교와 409 입력 보존 규칙도 그대로입니다. 프로덕션 변경은 화면 파일 두 개(`web/src/resource-form-state.ts`, `web/src/resources.tsx`)이며 Go 프로덕션 변경은 없습니다. 범위 안의 값이 만드는 요청 본문은 한 글자도 달라지지 않습니다.

이번 릴리즈는 화면이 제출하는 값만 고치므로, 이전 버전에서 이미 서버 범위를 벗어난 상한까지 올라갔다가 `400` 으로 잃어버린 입력은 되살리지 않고, 소수점이 잘려 저장된 과거 값도 자동으로 되돌리지 않습니다. 해당 범위·정책은 값을 다시 확인해야 합니다. 폼 제출 값 검사는 v1.21.0 에서 일시 칸에, v1.22.0 에서 JSON 칸에 같은 방식으로 들어왔고 이번에는 같은 폼의 숫자 칸을 맞췄습니다.

## 검증과 배포

새 공유 벡터 `internal/app/testdata/resource-number-bounds.json` 이 일곱 칸의 `min`·`max`·정수 잠금을 한 곳에 적습니다. Go 쪽 `internal/app/resource_number_bounds_test.go` 는 그 칸을 **다시 적지 않고 거기서 탐침을 만들어** 실제 `validateScope`·`validatePolicy` 에 넣습니다. `min` 은 통과, `min-1` 은 거절, `max` 는 통과, `max+1` 은 서버 자신의 문구로 거절되는지 확인하므로 그 두 칸이 서버의 실제 허용 범위임이 벡터 밖에서 증명됩니다. 같은 시험은 소수점 제출이 잘려 저장되는 것도 검증기에 직접 넣어 확인합니다. 화면 쪽 `web/tests/resource-number-bounds.test.mjs` 는 같은 벡터로 `resourceNumberBounds` 가 정확히 일치하는지, 일곱 선언이 모두 그 표를 펼쳐 쓰는지, 서버가 자르는 칸이 정수 전용으로 선언됐는지 단언합니다.

`npm --prefix web ci` 후 `npm --prefix web test` 가 `web/tests` 20개 파일에서 113개 검사를 실행해 모두 통과했고 실패·건너뜀은 0개입니다. 수정 전 선언(초당 최대 요청 수 `0.1`~`100`, 동시 실행 상한 최대 `20`, 최대 요청 수 최대 `1000`, 실행 제한 시간 최대 `600`, 소수점 허용)으로 되돌리면 새 화면 시험 두 개만 실패해 111통과/2실패가 되는 것을 먼저 확인했습니다. 같은 되돌림에서 Go 시험은 계속 통과합니다. Go 쪽이 화면 표가 아니라 서버 검증에서 판정을 얻기 때문이며, 이것이 벡터의 `min`·`max` 가 서버의 범위라는 근거입니다. 릴리즈 커밋에서 실행한 검사와 건너뛴 검사는 [검증 기록](validation.md)에 적었습니다.

브라우저에서 NumberInput 을 직접 타이핑하고 칸을 떠나 clamp 동작을 눈으로 확인하거나, PostgreSQL 이 붙은 서버에 실제로 저장해 재현하지는 않았습니다. PostgreSQL 이 필요한 Go 전체 시험은 이 환경에서 실행하지 않았습니다.

화면 캡처는 v1.9.0의 검증 장면을 보존했습니다. 가이드·README·llms.txt·openapi.json 의 버전 표기를 갱신하고 가이드 HTML·PDF 를 재생성했습니다.
