# 알림 채널 설계의 공식 근거

조사일: 2026-09-12. SMTP 표준, 공급자 API 문서와 Go 원본을 확인했습니다. 아래는 공급 계약의 차이와 Hunter 설계 판단을 구분한 기록입니다. 실제 제공 설정과 검증 범위는 [관리자 가이드](guides/admin-guide.md)에서 확인합니다.

## SMTP: 보안 연결 방식과 접수의 의미

RFC 8314는 메일 제출에 TLS 1.2 이상을 사용하고 Implicit TLS를 권장합니다. 통상 465번 포트의 Implicit TLS와 587번 포트의 STARTTLS를 구분하며, 둘 다 TLS 연결 성공을 필수로 요구하고 인증서를 검증해야 합니다. 사내 릴레이의 지정 포트는 별도 계약을 따릅니다. [RFC 8314](https://www.rfc-editor.org/info/rfc8314/)

Go `net/smtp.SendMail`은 서버가 지원할 때 TLS로 전환하는 하위 수준 도구입니다. 따라서 필수 STARTTLS 설정은 애플리케이션이 지원 여부·협상 실패를 검사해 중단해야 합니다. TLS를 지원하지 않는 서버에 계정 비밀번호를 보내는 대체 경로를 만들지 않습니다. [Go 1.26.5 SMTP 원본](https://github.com/golang/go/blob/go1.26.5/src/net/smtp/smtp.go)

Hunter의 설계 판단은 보안 모드를 명시적으로 고르고 사내 CA를 적용하는 것입니다. 평문 옵션이 필요한 기존 릴레이는 무인증 사내 릴레이 계약으로 제한합니다. SMTP 서버의 접수 응답은 최종 수신자의 받은편지함 표시나 읽음 확인과 구분합니다.

DATA 종료 뒤 250 응답은 SMTP 서버가 전달·중계 책임을 수락했다는 의미입니다. 종료 표시를 보낸 뒤 응답을 확인하지 못한 경우 재전송하면 중복 메일이 생길 수 있습니다. Hunter의 결과 불명 상태와 자동 재발송 제외는 이 경계를 고려한 설계입니다. [RFC 5321 §6.1](https://www.rfc-editor.org/rfc/rfc5321.html#section-6.1)

## 문자: 공급자 인증과 한글 길이

NAVER Cloud는 access key, 밀리초 타임스탬프와 HMAC-SHA256 서명을 사용합니다. 서명 대상에는 HTTP 메서드, 쿼리를 포함한 URI, 타임스탬프와 access key가 포함되며 헤더의 타임스탬프와 같아야 합니다. 서버 시각과 5분 이상 차이가 나면 요청을 거부합니다. [Ncloud API 서명](https://api.ncloud-docs.com/docs/en/common-ncpapi)

SENS SMS는 등록된 발신번호를 요구합니다. 해당 API의 SMS·LMS 길이는 EUC-KR 바이트 기준이며 지원하지 않는 이모지나 길이 초과의 처리가 따로 정의되어 있습니다. 이는 Hunter의 UTF-8 입력 제한과 같은 기준이 아닙니다. 메시지 유형, 발신번호, 국가번호와 길이는 선택한 공급자의 계약을 확인해야 합니다. [SENS 문자 발송](https://api.ncloud-docs.com/docs/en/sens-sms-send)

따라서 범용 HTTP 전송만으로 모든 문자 공급자와 자동 호환된다고 설명하지 않습니다. 인증, JSON·폼 본문, 성공 판정과 접수 ID를 공급자 또는 사내 게이트웨이 계약에 맞춰 연결합니다. 공급자 전용 토큰 발급이나 추가 서명 절차가 있다면 지원되는 인증과 일치하는지 먼저 확인합니다.

## 알림톡: 발신프로필·템플릿·결과 계약

NHN Cloud의 알림톡 API는 appkey, `X-Secret-Key`, 발신 키와 템플릿 코드를 사용하며 치환값을 별도로 전달합니다. 템플릿에는 검수·승인·반려 상태가 있습니다. 응답 본문의 성공 여부와 결과 코드를 확인해야 하며 공급자에 문자 대체 발송이 설정되어 있을 수도 있습니다. [NHN Cloud 알림톡 API](https://docs.nhncloud.com/ko/Notification/KakaoTalk%20Bizmessage/ko/alimtalk-api-guide-v2.2/)

Kakao i Connect Message는 별도 OAuth 인증과 발신 키·템플릿 코드를 요구하며 계약에 따라 결과 확인 방식도 구분합니다. 알림톡은 허용되는 정보성 메시지에 한정됩니다. 따라서 사내 보안 공지라는 이유만으로 템플릿 심사를 통과한다고 가정할 수 없습니다. 메시지의 문구·치환자·버튼과 대체 발송은 계약한 제공자의 승인 내용에 맞춰야 합니다. [Kakao i 알림톡 발송](https://docs.kakaoi.ai/kakao_i_connect_message/bizmessage/api/api_reference/at/)

Hunter의 알림톡 채널은 카카오 앱 로그인이나 개인 계정의 메시지 보내기 기능과 구분합니다. 실제 수신자 번호, 발신프로필, 승인 템플릿과 계약 자격 정보는 조직에서 준비합니다. 자동 문자 대체 발송을 함께 사용하면 중복 비용과 중복 통지가 생길 수 있으므로 어느 계층이 대체 발송을 담당하는지 정합니다.

## 폐쇄망과 검증 범위

Hunter 자체는 사내 PostgreSQL과 같은 네 환경변수의 배포 구조를 유지합니다. 메일은 접근 가능한 사내 릴레이, 문자·알림톡은 조직이 허용한 API 경로가 필요합니다. 외부 통신이 없는 망에서 통신사·카카오까지 전달하려면 승인된 중계망이나 사내 게이트웨이가 있어야 합니다.

전달 요청의 접수와 단말 도달을 구분하고, 접수 뒤 연결이 끊긴 결과를 성공 또는 미발송으로 단정하지 않는 것이 설계 원칙입니다. 접수 ID·정규화한 오류·시도 이력을 남기되 수신자 정보, 인증 헤더와 공급자 응답 원문이 일반 로그나 감사 본문으로 노출되지 않도록 합니다.

개발 검증에는 로컬 모의 SMTP·HTTP 서버와 합성 주소·번호를 사용합니다. 실제 공급 계정, 발신번호 등록, 알림톡 템플릿 승인·과금·단말 도달은 이 검사로 검증한 것이 아닙니다. 외부 실수신자에게 시험 메시지를 발송하지 않습니다.
